# Пропозиція розширення VIP — НЕ застосована

Для Grant/Revoke/редагування опису потрібен доступ до одного живого m_EGC_VIPConfig. Сьогодні публічний контракт надає лише EGC_IsPlayerVIP; EGC_VIPConfig.Save повертає void і не повідомляє про відмову запису.

Пропоноване місце: **новий** `Scripts/Game/EGC_AdminTools/EGC_AdminVipBridge.c`, `modded class SCR_BaseGameMode`; оригінальний `EGC_VIPManager.c` фізично не змінюється. Це все одно розширення поведінки EGC-класу, тому до погодження файл не створюється в активному mod.

Пропонований контракт:

```
bool EGC_AT_ChangeVip(int actorId, int targetPlayerId, bool enabled, string description, out string result)
```

Алгоритм:

1. Лише сервер; actor визначено контролером, повторна перевірка EGC_AdminAccess; UID цілі резолвить backend, перевіряє знімок каналу.
2. Переконатися, що наявний m_EGC_VIPConfig ініціалізований. Ніякого нового global VIP config.
3. Відмовити у видачі VIP гравцеві з ADMINISTRATOR/SESSION_ADMINISTRATOR, щоб не спровокувати kill/kick чинним watchdog. Не знімати ролі автоматично.
4. Змінити тільки UID -> опис в існуючому об'єкті; викликати його Save.
5. Оскільки Save не повертає bool, перечитати файл сучасним JsonLoadContext і порівняти **всю** карту з очікуваною. При невідповідності повідомити INDETERMINATE, перечитати живий конфіг через його Load і заблокувати наступні записи до звірки; не повідомляти успіх.
6. Аудит actor UID, target UID, операції, причини й результату. Запит не приймає довільний target UID з UI.

Ризики: зовнішній редактор файла може працювати одночасно; Save не гарантує атомарність і перевірка після запису не є транзакцією. Для повної надійності потрібен окремо погоджений перегляд збереження всередині EGC_VIPConfig. У першій інтеграції слід мати одного writer та резервну копію силами сервера.

Альтернатива без розширення GameMode: залишити панель read-only; чинний адміністратор змінює EGC_Vips.json у встановленому EGC-процесі, watchdog перечитує до 300 секунд. Це поточний реалізований варіант.

Строк дії/подовження не включені: у поточній моделі EGC немає expiry. Додавання expiry було б зміною правил VIP і потребує окремої специфікації та погодження. Не додавати паралельний scheduler або файл VIP до нової адмінки.
