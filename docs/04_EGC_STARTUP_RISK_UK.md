# Критичний ризик старту в оригінальному EGC — без змін

Це результат статичного читання, не відтворений crash/freeze у грі.

Ланцюжок:

1. `EGC_BanSystem.c:3–5` оголошує загальні поля SCR_BaseGameMode: m_bIsRplStreamReady=false, шлях security.bin та m_iCoreModifier.
2. `EGC_GraphicsGuard.c:150–178`: OnGameModeStart, для rpl && !rpl.IsProxy(), планує SCR_UpdateRemoteSession через 15000 мс.
3. `EGC_GraphicsGuard.c:225–245`: SCR_UpdateRemoteSession читає `$profile:EGC_config/security.bin`, порівнює рядок із розрахованим значенням, тільки при збігу ставить прапорець true; потім планує SCR_CheckSessionProtocol через 10000 мс. `buf.Trim()` повертає новий string, але результат не присвоєний — пробіли можуть залишатися.
4. `EGC_GlobalChatControl.c:141–158`: SCR_CheckSessionProtocol виконує `while (!m_bIsRplStreamReady)`, генерує випадкові адреси та безперервно друкує «memory corruption». Усередині немає yield, таймера, break або зміни прапорця.

За відсутнього/неправильного файла очікується зависання скриптового потоку та заповнення журналу приблизно через 25 секунд після події старту на авторитетній сутності. Ці повідомлення самі по собі не доводять пошкодження пам'яті: адреси генеруються кодом випадково.

Адмінка не повинна створювати security.bin, підміняти прапорець чи викликати ці методи. EGC_BanSystem тому має додаткові приховані залежності від GraphicsGuard/GlobalChat, хоча за назвою виглядає окремим експортером банів. Перенесення тільки BanSystem до нового addon не є незалежним комплектуванням EGC.

## Конкретна мінімальна пропозиція для діагностичного стенда — НЕ застосована

Файл `EGC_GlobalChatControl.c`, замінити **тільки тіло** SCR_CheckSessionProtocol:

```c
protected void SCR_CheckSessionProtocol()
{
    if (!m_bIsRplStreamReady)
        Print("[EGC] Session configuration check failed; inspect server configuration.", LogLevel.ERROR);
}
```

Причина: усунути безкінечний цикл і фальшиві повідомлення про пам'ять. Ризик: це змінить чинну реакцію на неправильний security.bin на одноразову діагностику; якщо перевірка має бути умовою допуску до роботи, така заміна сама по собі не зберігає intended enforcement. Для production потрібно спочатку з'ясувати призначення перевірки та погодити керовану відмову запуску замість зависання.

Альтернатива без зміни оригіналу: використовувати повністю налаштоване чинне EGC-середовище з передбаченим власником provisioning security.bin; перевірити його на тестовій копії сервера. Це не виправляє помилку для майбутньої відсутності/пошкодження конфігурації. Новий мод не виправляє і не обходить цю поведінку самостійно.
